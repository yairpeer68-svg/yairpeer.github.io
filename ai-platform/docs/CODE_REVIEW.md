# Code Review — 2.0.0

## Architecture

The system is split into FastAPI API, repositories/services, AI provider gateway, persistence, middleware/monitoring, Dramatiq workers, React Admin, Flutter Android and deployment assets. API versioning is rooted at `/api/v1`. PostgreSQL is authoritative for durable state; Redis is used for rate limits, quota reservations, cache and maintenance/circuit state. DeepSeek is behind an `AIProvider` abstraction.

The major boundaries are explicit and replaceable: AI provider, push provider, payment provider, attestation verifier and email delivery. Missing external adapters return/fail as **not configured**, never as fake success.

## Correctness

The review specifically re-checked token rotation/reuse, device/session rebinding, revoked-device use, quota reservation/release, AI cache accounting, provider failure mapping, request-ID propagation, admin authorization, migrations and app-version enforcement. Fixes made during review are recorded in `SECURITY_REVIEW.md`.

The initial Alembic revision creates the full 23-table model set (the two account-token tables are generated by a migration loop), creates indexes/constraints, and seeds initial feature flags plus Android app version metadata. Production startup uses Alembic; there is no `Base.metadata.create_all()` production path.

## Maintainability

Backend responsibilities are separated by package and interfaces rather than concentrated in route handlers. Configuration is centralized in Pydantic settings with production validation. Error responses are normalized through `AppError`. Cleanup, backup, install, upgrade and verification have dedicated commands/scripts.

Several source files intentionally favor compact implementation over exhaustive internal framework abstraction. Future growth should split `admin.py` and some Flutter screens into smaller feature modules once the UI becomes larger.

## Performance

- Async SQLAlchemy and HTTPX are used for request-path I/O.
- DB engine uses pre-ping, recycling and bounded pooling.
- Redis Lua performs atomic rate-limit and quota reservation operations.
- AI response caching is keyed by model + normalized prompt hash + temperature + max tokens.
- DeepSeek HTTP client applies connection limits, timeout and bounded exponential backoff.
- Pagination caps admin list sizes; AI history is capped.
- Prometheus histograms/counters cover HTTP and AI latency/errors.

A production load test is included under `tests/load/k6.js`, but was not executed in this environment.

## Security

Authentication, authorization, prompt privacy, secret handling, CORS/trusted-host checks, rate limiting, container isolation and Nginx headers were reviewed. The strongest remaining security uncertainty is third-party dependency state because offline dependency scanners could not run locally; CI is configured to close that gap.

## Recommended next improvements

- Add real Google Play Integrity verification and FCM adapters before relying on device trust/push delivery.
- Add the chosen real payment provider only after its webhook/signature implementation is independently reviewed.
- Add a generated, committed npm lockfile and Flutter lockfile from an online trusted build runner for stronger dependency reproducibility.
- Run integration/load tests against production-like PostgreSQL/Redis and record baseline p95/p99 latency and DB pool saturation.
- Add end-to-end browser and Android integration tests once the CI environment has emulator/browser runners.
